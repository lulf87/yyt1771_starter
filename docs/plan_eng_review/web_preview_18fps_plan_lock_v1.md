## Purpose

这份文档把“如果最终 operator preview 目标是约 `18 fps`，Web 是否还能作为最终交付壳”锁成一个可执行的工程计划。

它重点锁 5 件事：

1. delivery shell 的决策顺序如何改变
2. 哪些模块边界保持不变，哪些配置/显示点需要调整
3. 现有 workflow 与状态流如何原样保留
4. API / 配置契约应如何最小改动支持这条 gate
5. 测试、bench 和最终 decision gate 如何分阶段完成

## 1. Locked Decision Tree

这棵决策树是原始 2026-03-24 gate 的历史记录；`mac-finish` 后当前结果
已经校准为 Web workstation first。

历史决策顺序为：

```text
same workflow + same core
        |
        v
run explicit Web 18 fps viability gate
        |
        +-- PASS --> Web may remain final delivery shell
        |
        +-- FAIL --> desktop migration would have remained primary delivery path
```

这意味着：

- desktop migration 当时不会被自动取消
- 但它也不再因为历史方向而自动赢下最终交付权
- `mac-finish` 后当前结论是 Web 工作站作为 active shell 继续推进

## 2. Locked Architecture Decision

### 2.1 Shared architecture does not change

固定系统方向继续保持：

```text
Delivery Shell (desktop_app | webapp) -> Application Layer -> Workflow / Storage / Report
```

分析链继续保持：

```text
Frame -> ShapeMetric -> SyncPoint -> Curve -> Result
```

这条 Web 18 fps workstream 不改变系统架构，只改变“哪个 shell 仍有资格成为最终交付”的决策顺序。

### 2.2 Web viability work must stay inside current module boundaries

这条 workstream 必须继续复用当前共享内核：

- `src/core`
- `src/application`
- `src/workflow`
- `src/storage`
- `src/report`
- `src/curve`
- `src/camera`
- `src/temp`

不允许为这条 Web gate 新建第二套 preview coordinator、第二套 run state、或第二套 artifact 逻辑。

### 2.3 Desktop path is paused fallback, not deleted work

当前工程建议不是：

- 停止 desktop migration

而是：

- 在 Web 工作站路线已被 `mac-finish` 选定后
- desktop migration 视为暂停的历史 / fallback reference

这让当前已做完的 D1-D5 和部分 D6 继续保留工程价值，但不再主导最终交付结论。

## 3. Workflow and State Lock

### 3.1 Workflow semantics remain unchanged

Web viability work 不允许更改这些动作语义：

- `precheck`
- `probe`
- `create run`
- `start preview`
- `stop/freeze preview`
- `ROI / 观测窗口 / A-B` 定义
- `start live run`
- `telemetry / result / artifact review`

### 3.2 Durable run state does not change

这条 workstream 不新增 durable run lifecycle。

继续沿用现有 shared workflow / run state 语义。

### 3.3 Freeze-first setup semantics remain shared

Web 要过 gate，必须继续保留：

- `Stop Live Preview` 保留最后一帧
- 同一 run 内可 restart preview
- ROI / 观测窗口 / A-B 可视化编辑

不允许为了追 `18 fps` 把这些 operator 语义降级掉。

## 4. Locked Config and API Contract

### 4.1 Acquisition profile strategy

第一阶段锁定为：

- `setup_preview` 与 `measurement` 允许先共享同一 acquisition ROI
- 不强制 full-frame
- 第一轮候选 profile：

```text
trigger_mode = free_run
pixel_format = mono8
exposure_us = 12000
gain_db = 3.0
device_roi = x=384, y=256, width=2304, height=1536
preview_target_fps = 18
preview_poll_ms = 56
```

这组值当前定义为：

- requirement-aligned candidate baseline
- 不是已验证通过的最终现场结果

### 4.2 Web preview output size must become configurable or explicitly raised

当前 Web route 里仍然存在 operator-visible size 硬上限：

- stream max width = `384`
- stream max height = `256`

这条 workstream 不能只改 camera ROI，不改显示尺寸。

工程建议锁定为：

- 第一轮目标 output size 约 `768 x 512`
- 实现上允许两种方式：
  - A. 先把当前常量提升到该级别
  - B. 抽成 config-driven preview presentation contract

Opinionated recommendation:

- 选 B，但实现要保持 minimal diff
- 原因：这条 gate 本来就是“最终 delivery shell 决策条件”，不应再隐藏成路由内部 magic number

### 4.3 Existing Web API surface should remain stable

这条 workstream 不应新开第二套 preview route。

继续沿用：

- `POST /api/runs/{run_id}/preview/frame`
- `GET /api/runs/{run_id}/preview/stream`
- `POST /api/runs/{run_id}/preview/stream/stop`
- `GET /api/runs/{run_id}`

允许变化的是：

- preview image size
- preview cadence
- rates / detail 中的事实值

不允许变化的是：

- route shape
- frozen-frame semantics
- current run-detail contract 的核心结构

### 4.4 Measurement cadence contract remains separate

这条 Web plan 明确保持：

- `preview_display_fps >= 18` 是 Web operator gate
- `measurement_sample_hz >= 50` 仍由 temporal-sampling requirement 管

任何实现若把两者重新混成一个“刷新率”数字，应视为 plan drift。

## 5. Test and Bench Lock

### 5.1 Code-level regression gate

每轮改动必须继续保持：

- config loader tests
- preview service tests
- camera adapter tests
- live run API tests
- UI shell tests

### 5.2 Web viability bench must be explicit

新的 Web gate 不允许只靠体感。

至少要记录：

- profile 名称
- camera ROI
- pixel format
- exposure / gain
- target preview fps
- preview output size
- measured `preview_display_fps`

### 5.3 Bench staging order

bench 顺序锁定为：

```text
Mac proxy bench
    ->
Windows same-profile bench
    ->
decision gate
```

原因：

- Mac 适合快速试参数
- Windows 才是最终验收环境

### 5.4 Decision gate

若 Web 要继续作为最终交付候选，必须同时满足：

1. `preview_display_fps >= 18`
2. display size 明显大于当前 `384 x 256`
3. 亮度达到 operator 可用
4. freeze / restart / overlay edit 语义不回归
5. Windows 环境下完成正式验收

未同时满足时，不得宣称“Web 已足够替代 desktop”。

## 6. Staged Execution Order

### Phase W1: Requirement and plan lock

- requirement 已落地：
  - [web_preview_18fps_requirement_v1.md](../requirements/web_preview_18fps_requirement_v1.md)
- 当前文档锁定实施顺序

### Phase W2: Config/presentation contract patch

- 把 candidate preview profile 落到本地 / bench profile
- 提升或抽出 Web preview output size contract
- 保持现有 API surface 不变

### Phase W3: Web preview implementation pass

- 让 Web 真正吃到新的 `setup_preview` / `measurement` profile
- 确认 brightness / ROI / output size / cadence 一起生效

### Phase W4: Mac proxy bench

- 在 Mac 上记录第一轮正式 Web viability 结果
- 明确是：
  - PASS_TOWARD_WINDOWS
  - or FAIL_AND_KEEP_DESKTOP_PRIMARY

### Phase W5: Windows acceptance bench

- 用同一 profile 在 Windows 上完成正式 bench
- 记录最终 `preview_display_fps`
- 给出 final gate verdict

### Phase W6: Delivery-shell decision

- 如果 W5 pass：
  - Web 升级为 final delivery candidate
  - desktop path 降级为 optional optimization path
- 如果 W5 fail：
  - desktop migration 恢复为明确 primary path

## 7. Opinionated Recommendation

最稳的执行顺序不是“继续默认 desktop”，也不是“现在就宣布 Web 足够”，而是：

```text
lock requirement
  ->
lock explicit Web gate
  ->
run narrow Web bench
  ->
decide final shell
```

这是最小风险、最少返工、也最符合当前仓库真实积累的路线。
