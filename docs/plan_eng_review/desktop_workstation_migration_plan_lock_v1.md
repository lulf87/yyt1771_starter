## Purpose

这份文档把“在原仓库里做桌面迁移”的方向锁成可执行工程计划。

它重点锁 5 件事：

1. 哪些模块保留，哪些模块先抽离
2. 桌面迁移的首批目录与边界
3. workflow 与状态流如何保持不变
4. 测试和验收如何分层
5. 分阶段实施顺序如何安排，才能最大化复用当前成果

## Review Verdict

Recommendation:

- 保留当前仓库作为唯一实现主线
- 不另开新的 Python 项目
- 先抽应用层，再加桌面壳
- 浏览器层降级为过渡适配层，不再当最终交付方向

Rejected:

- 先写新的桌面 UI，再想办法把当前 `webapp` 代码硬接进去
- 在没有跨语言决定前，立刻另开一个新的 Python 项目复制现有核心逻辑
- 把当前 MJPEG 路由当成桌面预览主路径

## 1. Locked Architecture Decision

### 1.1 Same repository, new delivery shell

新的桌面迁移在当前仓库中完成。

架构上的目标不是：

- `web -> desktop` 两套业务内核并存

而是：

- 一套共享业务内核
- 两层可替换的交付壳
  - `webapp`：过渡/调试/legacy 壳
  - `desktop_app`：新的目标交付壳

### 1.2 Extract application layer before building the desktop UI

新的桌面 UI 不能直接依赖当前 `webapp/deps.py`。

因此必须先建立一个共享 application layer。

推荐目标结构：

```text
src/
  application/
    runtime_config.py
    live_preview_service.py
    live_run_service.py
    live_run_registry.py
    device_factory.py
  desktop_app/
    ...
  webapp/
    ...
```

这里的目录名不是绝对硬锁，但职责边界是硬锁。

### 1.3 PySide6 / Qt is the default desktop path

在当前阶段，桌面壳默认采用：

- `PySide6 / Qt`

原因：

- 与现有 Python 业务内核共享最直接
- 允许 Mac 上继续做桌面 UI 开发
- 最终仍可在 Windows 上打包与验收

## 2. Module Boundary Lock

### Keep as shared core

以下模块保留为共享核心，不作为首轮迁移的重写对象：

- `src/core`
- `src/workflow`
- `src/storage`
- `src/report`
- `src/curve`
- `src/temp`

### Keep but treat as "reuse + optimize"

以下模块保留，但允许在桌面迁移中继续做性能改造：

- `src/camera`

特别是：

- `HikGigeMvsCamera` 继续作为主相机采集起点
- 但桌面显示链不应被当前 Web 预览路径绑死

### First extraction targets

以下文件/职责必须在桌面壳开工前先抽离：

- `src/webapp/config.py`
- `src/webapp/deps.py`

应迁出的职责包括：

- runtime config/profile loading
- local override merge
- `setup_preview` / `measurement` acquisition profile loading
- `LivePreviewService`
- `LiveRunService`
- `LiveRunDraftRegistry`
- camera/temp controller build logic
- application-level ephemeral state

### Keep as thin web adapter later

`src/webapp/` 在迁移后应只保留：

- route/schema/template/static 这类 Web 适配职责
- 对 application layer 的薄调用

不应再继续作为：

- 共享应用层事实来源
- 桌面端必须依赖的容器层

## 3. Workflow and State Lock

### 3.1 Workflow semantics do not change

桌面迁移不改变以下工作流语义：

- `precheck`
- `probe`
- `create run`
- `start preview`
- `stop/freeze preview`
- measurement definition
- `start live run`
- telemetry / result / artifact review

### 3.2 Durable run state remains shared

当前的 durable run lifecycle 仍应继续由共享 core/workflow 负责。

桌面迁移不应重发明第二套 run lifecycle enum。

### 3.3 Freeze-first setup semantics remain shared

下面这些 UI 语义仍然视为共享产品规则，而不是 Web 专属规则：

- `Stop Live Preview` 保留最后一帧
- 同一 run 内可 restart preview
- ROI / 观测窗口 / A-B 可视化编辑

桌面 UI 只是新的承载方式。

---

## 4. Application-Layer Lock

### 4.1 Required services

新的共享 application layer 至少应包含：

1. `RuntimeConfigService`
   - 负责 profile loading / local override

2. `DeviceFactory`
   - 负责构建 camera / temp controller / related adapters

3. `LivePreviewService`
   - 负责 preview session、freeze、latest-frame 策略

4. `LiveRunRegistry`
   - 负责 run draft / ephemeral state

5. `LiveRunService`
   - 负责 run start / stop / active execution state / callback bridge

### 4.2 What application services must not own

application layer 不应承担：

- Qt widget layout
- HTML template rendering
- HTTP route concerns
- Windows packaging steps

它的职责是：

- 给 `webapp` 和 `desktop_app` 提供同一组可调用服务

---

## 5. Desktop UI Lock

### 5.1 First desktop milestone

桌面 UI 的第一阶段不追求“功能全量重做”，而是只接通最小可用主链：

1. profile loading
2. precheck
3. camera probe
4. create run
5. preview start/stop/freeze
6. ROI / 观测窗口 / A-B 编辑
7. start live run
8. result / telemetry readback

### 5.2 Do not overdesign native preview architecture in phase 1

Phase 1 的桌面预览目标是：

- 摆脱当前 Web MJPEG 交付路径
- 验证桌面 UI 可以直接消费共享 preview/application service

Phase 1 不要求一次性解决：

- 最终最优高 FPS rendering implementation
- 所有 Windows packaging polish

但它必须为这些能力留出清晰边界。

## 6. Config Lock

### 6.1 Fix the current camera baseline issue

在开始桌面迁移前，应先统一配置方向：

- MVS 作为桌面迁移的默认相机主路径
- RTSP 不再作为这条主线的默认开发路径

这不是建议项，而是 D2 的显式交付项。

### 6.2 Fix the current temp backend naming mismatch

当前温控 backend naming 和实际 service 识别逻辑存在不一致。

这必须在桌面迁移的早期阶段修正，否则：

- application layer 抽离后仍会带着错误契约前进

这同样不是叙述性提醒，而是 D2 的显式交付项。

### 6.3 Preserve setup/measurement split

当前已经存在的：

- `setup_preview`
- `measurement`

两套采集 profile 继续保留，并且必须进入共享 config/application 层，而不是继续锁在 `webapp`。

## 7. Testing and Verification Lock

### 7.1 Shared-core regression gate

每一轮迁移必须保证以下测试层先继续绿：

- core model tests
- workflow tests
- artifact/result tests
- camera/temp adapter tests

### 7.2 Application-service regression gate

抽离 application layer 后，必须新增或迁移测试来覆盖：

- config loading
- preview service behavior
- run registry behavior
- device factory decisions
- live run service state transitions

### 7.3 Web parity gate

在桌面壳尚未完全接管前，`webapp` 仍应保持可运行。

目的不是继续做 Web 最终产品，而是：

- 作为迁移过程中的 parity oracle

### 7.4 Desktop integration gate

桌面端必须新增：

- desktop smoke tests
- presenter/controller-level tests
- preview state tests

### 7.5 Windows acceptance gate

最终必须在 Windows 上完成：

- MVS runtime validation
- preview performance validation
- serial / temp-controller validation
- packaged product smoke

并且从现在开始，desktop preview 必须有独立于 measurement cadence 的验收口径：

- 在声明清楚的 Windows bench profile 下
- 使用 desktop preview path
- 记录 device ROI / pixel format / exposure / gain / target fps
- 满足 `preview_display_fps >= 50`

未达到这组条件时，不得把“桌面预览 >50 Hz”宣称为已完成。

## 8. Phase Order

### Phase D1: Documentation Lock

- 新增 desktop migration requirement
- 新增 desktop migration plan lock
- 更新 canonical entry docs

### Phase D2: Shared config extraction

- 把 `webapp/config.py` 抽成共享 runtime/config 层
- 迁移现有测试
- 把 MVS 固化为桌面迁移主路径的默认相机基线
- 修正 temp backend naming mismatch

### Phase D3: Application-service extraction

- 把 `LivePreviewService`
- `LiveRunService`
- `LiveRunDraftRegistry`
- device build logic
  从 `webapp/deps.py` 抽到共享 application layer

### Phase D4: Web thin-adapter refit

- 让 `webapp` 改为调用新的 application layer
- 保持现有 Web 路径继续可运行

### Phase D5: Desktop shell bootstrap

- 新增 `desktop_app`
- 接通最小可用 workflow 主链

### Phase D6: Desktop preview optimization

- 针对桌面显示路径做 preview 性能改造
- 不再依赖 Web MJPEG route 作为最终显示方案
- 以 `preview_display_fps >= 50` 的 Windows desktop preview gate 作为本阶段目标

### Phase D7: Windows packaging and field gate

- Windows runtime validation
- packaged-product validation
- final acceptance
- 在 Windows 上完成桌面预览 gate、相机 runtime gate、串口 / 温控 gate 的收口

---

## 9. Recommendation

当前最优执行路线是：

1. 在原仓库中继续推进
2. 先抽 `config` 和 `deps` 里的应用层
3. 再引入 `PySide6 / Qt` 桌面壳
4. 把 Web 降级为过渡适配层
5. 最终在 Windows 上收敛打包与现场验收

这条路线风险最低，且能最大化复用当前已验证成果。
