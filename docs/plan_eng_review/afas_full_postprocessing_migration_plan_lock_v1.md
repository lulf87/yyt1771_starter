## Purpose

这份文档把“将 `AFAS/` 中拿到数据后的完整后处理能力迁入当前项目”锁成一条可执行工程计划。

它锁定 6 件事：

1. 当前轻量 live `afas.py` 和完整 AFAS 后处理产品之间的工程边界
2. 新的完整后处理 pipeline 应该落在哪些模块里
3. 当前 artifact / result / workspace contract 需要怎样扩展
4. 多通道、预处理、参数化切线分析、图表、导出应该按什么顺序落地
5. 如何在不打断现有 live run 主链的前提下完成迁移
6. 什么时候才能诚实地说“AFAS 全量后处理迁移完成”

---

## Review Verdict

Recommendation:

- 不要把“完整 AFAS 迁移”硬塞进当前轻量 live `afas.py`，让 live run 主链承担全部后处理产品职责
- 保留当前轻量 live result path，继续服务：
  - run 中即时结果
  - result contract
  - artifact summary
- 同时新增一条**完整 postprocessing pipeline**
  - 专门负责 `AFAS/` 风格的：
    - 预处理
    - 平滑
    - 参数化切线分析
    - 多通道总览
    - 结果面板
    - PNG / Excel 导出

Opinionated recommendation:

- 用“**双层 AFAS 路线**”而不是“重写现有 live AFAS”为主方案
- 原因：
  - minimal diff 更好
  - 风险更低
  - 可测试性更高
  - 不会把当前已验证的 live run/result contract 一起打碎

Rejected:

- 直接把当前轻量 `afas.py` 扩成一个混合 live/offline/product UI 超级模块
- 为了 AFAS parity 先重写 live run workflow
- 在未完成预处理 / 图表 / 导出前继续把当前项目表述成“已经包含 AFAS 中所有拿到数据后的功能”

## 1. Locked Architecture Decision

### 1.1 Two-layer AFAS architecture is required

新的 AFAS 实现路线冻结为：

```text
Live acquisition / workflow
        |
        v
lightweight live AFAS result path
        |
        +--> current run/result contract
        |
        +--> persisted postprocessing dataset
                 |
                 v
          full AFAS postprocessing pipeline
                 |
                 +--> overview
                 +--> single-channel analysis
                 +--> result panel
                 +--> PNG / Excel export
```

这意味着：

- 当前轻量 live AFAS 保留
- 完整 AFAS parity 通过新的 postprocessing pipeline 落地
- 两条路径共享数据，不共享职责

### 1.2 Shared system direction does not change

固定架构继续保持：

```text
Delivery Shell -> Application Layer -> Workflow / Storage / Report
```

AFAS 迁移不会推翻：

- `src/workflow`
- `src/storage`
- `src/report`
- `src/webapp`

的现有边界，只会在其上新增完整 postprocessing 能力。

### 1.3 Full AFAS parity is post-data, not acquisition-first

这条 workstream 的 scope 起点锁定为：

- 已有结构化温度-形变量数据
- 已可生成 postprocessing dataset

它不是：

- 相机采集重构
- live setup 重构
- 温控控制重构

这些继续由现有 live-run / geometry / temperature workstreams 负责。

## 2. Boundary Lock

### `src/curve`

锁定职责拆成两层：

1. `live_afas`
   - 保留当前轻量 tangent-style live result path
   - 继续为 live run summary/result 提供最小可用分析

2. `afas_full_postprocessing`
   - 新增完整 AFAS 后处理能力
   - 包括：
     - 预处理
     - 参数化切线分析
     - 结果组织
     - chart/export 数据准备

Opinionated recommendation:

- 不要继续把所有逻辑都堆在 [afas.py](../../src/curve/afas.py)
- 应新增清晰拆分，例如：
  - `src/curve/afas_live.py` 或保留现名
  - `src/curve/afas_preprocessing.py`
  - `src/curve/afas_postprocessing.py`
  - `src/curve/afas_export.py`

但实现时应保持 minimal diff，避免为了“命名完美”做大范围搬家。

### `src/storage`

锁定新增职责：

- 持久化 postprocessing dataset
- 持久化完整分析结果
- 持久化 export artifact refs

当前 artifact 集合：

- `definition.json`
- `telemetry.csv`
- `events.jsonl`
- `detail.json`
- `result.json`
- keyframes

不足以承载完整 AFAS parity。

因此锁定新增方向：

- `afas_dataset.json` 或同等级结构化文件
- `afas_analysis.json`
- `afas_report.xlsx`
- `afas_plot.png`

### `src/report`

锁定职责：

- 继续服务轻量 live summary
- 新增完整 AFAS postprocessing summary / export metadata

不允许把完整 AFAS 面板语义继续压缩成当前只有 `as_value / af_value / af95 / reason` 的轻量结果摘要。

### `src/webapp`

锁定职责：

- 提供 postprocessing 入口与查看界面
- 允许用户选择通道、调参、重跑完整 AFAS 分析
- 展示 overview / analysis chart / results panel
- 提供导出入口

Opinionated recommendation:

- 不要硬把完整 AFAS UI 塞进当前 workspace 里已有的简化 SVG 区域
- 更合理的是：
  - workspace 保留 live evidence review
  - 新增 AFAS 分析视图或新 section
  - 让完整后处理成为明确的二级分析界面

### `src/workflow`

锁定职责：

- 继续产出 live run artifact
- 负责触发或调度 postprocessing dataset build
- 不负责实现 AFAS 图表、参数交互和导出细节

禁止：

- 把完整 AFAS UI 逻辑写进 workflow
- 把 export 逻辑塞进 live run coordinator

## 3. Locked Data Contract

### 3.1 Current live result contract remains valid

当前 live result contract 继续保留：

- `result_status`
- `reason`
- `detail`
- `as_value`
- `af_value`
- `af95`

这条 contract 不应因为完整 AFAS 迁移而被破坏。

### 3.2 New postprocessing dataset contract is required

完整 AFAS parity 必须新增一个 canonical postprocessing dataset contract。

最小字段锁定为：

- source session id / artifact provenance
- temperature series
- channel map
  - 允许单通道
  - 也允许 `Space1~Space6` 这类多通道
- preprocessing-ready numeric arrays
- optional timestamps

Opinionated recommendation:

- 不要直接让完整 AFAS 页面去读 `telemetry.csv` 的任意原始列拼图
- 应先构造一个稳定 dataset contract，再由后处理层消费

### 3.3 Multi-channel support is contract-level, not optional UI sugar

若数据源本身包含多个通道，则 contract 必须保留多通道结构，支持：

- overview chart
- channel selection
- selected-channel detailed analysis

这件事不能只靠前端约定或临时 CSV 解析完成。

### 3.4 Analysis parameter snapshot must be persistent

完整 AFAS 分析必须持久化当前分析参数：

- smoothing window
- polynomial order
- low-range
- high-range
- tangent offset
- outlier parameters

否则不能做到：

- 可复现分析
- 可比较参数调整前后差异
- 可导出完整报告

## 4. Implementation Sequence Lock

### APM-1. Postprocessing dataset contract first

先锁 dataset contract 和 artifact schema。

交付：

- dataset model
- artifact filename policy
- dataset build path from current session artifacts
- 单通道 / 多通道兼容策略

完成条件：

- 不改现有 live result path 的前提下
- 能稳定生成 postprocessing dataset artifact

### APM-2. Preprocessing parity

再迁移：

- temperature grouping
- outlier detection / repair
- Savitzky-Golay smoothing

参考实现：

- [preprocessing.py](/Users/lulingfeng/Documents/工作/开发/奥氏体变换/1771/AFAS/core/preprocessing.py)

完成条件：

- 当前项目里存在可测试的 preprocessing module
- 输出与 `AFAS/` 同等级的预处理结果结构

### APM-3. Parameterized tangent analysis parity

再迁移：

- parameterized tangent analysis
- max slope point
- low/high baseline fit
- tangent intersection
- outlier count / parameter summary

参考实现：

- [tangent_analysis.py](/Users/lulingfeng/Documents/工作/开发/奥氏体变换/1771/AFAS/core/tangent_analysis.py)

完成条件：

- 完整分析结果不再依赖当前轻量 `afas.py` 的简化逻辑
- 但 live run 仍可继续用轻量路径

### APM-4. Analysis UI parity

新增完整 postprocessing UI：

- overview chart
- selected-channel analysis chart
- results panel
- parameter controls

完成条件：

- 用户可在当前项目中完成一轮 AFAS 风格分析，而不是只看简化 workspace curve

### APM-5. Export parity

新增：

- PNG 300 DPI 导出
- Excel 报告导出

完成条件：

- 当前项目不再依赖 placeholder exporter
- 导出物可被 artifact 系统引用和回放

### APM-6. Fixture parity and regression

建立 AFAS parity fixtures：

- 使用 `AFAS/` 可代表性输入样例
- 对比：
  - preprocessing outputs
  - As / Af-tan
  - tangent/baseline params
  - exported artifact existence

完成条件：

- 可重复证明当前项目与 `AFAS/` 在关键分析能力上达成等价

## 5. Acceptance Lock

### 5.1 What counts as DONE

只有同时满足以下条件，才允许说：

> 当前项目已经具备 `AFAS/` 拿到数据后的全量后处理能力。

必须满足：

- preprocessing parity
- parameterized tangent-analysis parity
- channel overview parity
- results-panel parity
- PNG export parity
- Excel export parity
- fixture-based regression parity

### 5.2 What does NOT count as DONE

下面这些都不能单独算完成：

- `afas.py` 继续能算 `As / Af / AF95`
- workspace 上有一条曲线
- summary/result JSON 里多了几个字段
- 手工目测图表“看起来差不多”

### 5.3 Live path and full parity must be reported separately

状态汇报必须继续区分：

- `lightweight live AFAS`
- `full AFAS postprocessing parity`

不允许再把两者混成一个“AFAS 已完成”。

## 6. Test Strategy Lock

最小测试矩阵冻结为：

- `tests/curve/`
  - preprocessing parity
  - tangent-analysis parity
  - parameter edge cases
- `tests/storage/`
  - dataset artifact persistence
  - export artifact references
- `tests/webapp/`
  - analysis UI rendering
  - parameter update flow
  - export endpoints / download flow
- fixture parity tests
  - current project vs `AFAS/` representative outputs

Opinionated recommendation:

- 测试量应偏多，不偏少
- `AFAS/` 迁移属于典型“lake”，应该一次性把回归和导出路径都补齐

## 7. Locked Next Steps

从现在开始，AFAS 全量迁移的执行顺序锁定为：

1. `APM-1` dataset contract
2. `APM-2` preprocessing parity
3. `APM-3` tangent-analysis parity
4. `APM-4` analysis UI parity
5. `APM-5` export parity
6. `APM-6` fixture parity + acceptance

在 `APM-3` 完成前，不应再把当前项目对外表述成“已具备 AFAS 全量后处理能力”。
