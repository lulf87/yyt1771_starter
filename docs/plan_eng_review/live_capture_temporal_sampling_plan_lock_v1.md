## Purpose

这份文档把 temporal-sampling requirement 锁成可执行的工程计划。

它重点回答 5 件事：

1. 哪些模块需要为 `50 Hz synchronized measurement` 负责
2. 预览、定义、measurement run 三种状态如何分层
3. API 和 config 必须新增哪些契约，哪些不要新增
4. 测试如何区分 mock、integration、API、browser、bench
5. 分阶段实施顺序应该怎样排，才能先做对再做快

---

## Step 0: Scope Challenge

### What problem are we actually solving?

这次要解决的不是“页面看起来更顺”这么单一的问题，而是：

- setup 阶段的可操作性
- measurement 阶段的同步采样可信度
- bench 上真实 achieved rate 的可验证性

如果继续把这三件事混成一个“刷新率”目标，工程上会出现两种假完成：

- preview 刷新更快了，但 measurement cadence 仍然偏低
- 相机目标 fps 写高了，但 achieved rate、时间戳和 artifact 都无法证明

### Opinionated scope decision

Recommendation:

- 把 `setup preview fluidity` 和 `measurement cadence` 拆成两个 workstream
- 继续复用当前单 coordinator 架构
- 不在这一轮引入第二套 run engine、WebSocket event bus 或多进程采集

Reason:

- requirement 的新增内容是 profile split、camera-side ROI、achieved-rate reporting、bench gate
- 这些都可以在现有模块边界内完成

Rejected:

- 把 `50/100 Hz` 直接理解成 full-frame browser preview requirement
- 在未证明 `50 Hz` bench 可达之前，先上复杂实时架构

---

## Review Verdict

当前实现计划可以继续推进，但必须新增以下 5 条锁定原则：

1. `50 Hz` 的 baseline requirement 属于 measurement path，不属于 full-frame browser preview。
2. `setup_preview_mode` 和 `measurement_mode` 必须成为显式 config / contract 概念，而不是隐含约定。
3. `analysis_roi` / `metric_box` 只能定义分析区域，不能代替 camera-side acquisition ROI。
4. `RunStatus` 不为高频采样新增 durable enum；measurement mode 通过 run detail / telemetry / config profile 表达。
5. `100 Hz` 只保留为 stretch gate；没有真实 bench 证据前，不允许写成已完成能力。

## 1. Opinionated Recommendations

### Decision A. One coordinator vs. separate high-speed pipeline

Tradeoff:

- 新建独立高频 pipeline，理论上更纯粹，但会马上引入双状态机、双配置源、双 artifact 契约。
- 继续沿用现有 `workflow.live_run` coordinator，风险更低，diff 更小，但要求我们把 mode split 和 achieved-rate reporting 设计清楚。

Recommendation:

- 继续使用单 coordinator。
- 在 coordinator 内显式切换：
  - `setup_preview_mode`
  - `measurement_mode`

### Decision B. Keep preview stream alive during run vs. prioritize measurement cadence

Tradeoff:

- 运行时保持连续高频 browser preview，会和 measurement path 争抢相机、CPU、编码和网络预算。
- 运行时优先 measurement cadence，页面只显示低频监控帧或 keyframe，更符合 requirement，但 UI 观感上不如纯视频直观。

Recommendation:

- 运行中优先 measurement cadence。
- setup preview 是 setup 能力；run 阶段只承诺“监控可见”或 artifact 可回放，不承诺 full-rate preview parity。

### Decision C. Reuse analysis ROI vs. add camera-side acquisition ROI

Tradeoff:

- 只复用页面分析 ROI，前端交互简单，但无法从传感器/链路层真实降 payload。
- 新增 camera-side acquisition ROI / reduced readout 配置，会增加配置和适配器复杂度，但这是 `50 Hz` requirement 的必要条件。

Recommendation:

- 新增 measurement-mode acquisition ROI 契约。
- 明确与 `analysis_roi` / `metric_box` 分离。

### Decision D. Desired rates only vs. achieved-rate reporting

Tradeoff:

- 只暴露目标配置最简单，但 requirement 无法验收。
- 增加 achieved-rate reporting，需要在 camera/workflow/storage/webapp 都补字段，但能真正证明是否达到 `50 Hz`。

Recommendation:

- achieved values 必须进入 API、artifact 和 bench validation。

### Decision E. Build 100 Hz path now vs. gate after 50 Hz bench

Tradeoff:

- 直接冲 `100 Hz` 会把 camera-side ROI、曝光、照明、transport、extractor 性能、温度同步全都一次性拉高。
- 先锁 `50 Hz` baseline，再把 `100 Hz` 当 stretch gate，更容易让 bench 结果可解释。

Recommendation:

- 分阶段先完成 `50 Hz`，再决定是否进入 `100 Hz stretch`。

## 2. Module Boundary Lock

### `src.core`

新增职责：

- rate concept contracts
- camera acquisition profile models
- achieved-rate summary models

禁止新增：

- preview stream lifecycle code
- browser overlay state
- 相机 ROI 实际下发逻辑

### `src.camera`

新增职责：

- 应用 setup / measurement 两类 acquisition profile
- 暴露 resulting frame rate、payload、实际采集尺寸等 runtime facts
- 支持 camera-side ROI / reduced readout strategy 的 capability wiring

禁止新增：

- measurement cadence 计算
- preview transport 编码
- UI ROI / A-B / observation-window 语义

### `src.sync`

新增职责：

- 为温度与位移样本提供共享时间基准
- 聚合 cadence 统计所需时间戳

禁止新增：

- scheduler / event bus
- preview frame fan-out

### `src.workflow`

新增职责：

- 从 setup preview 切换到 measurement mode
- 维护 measurement tick 的 sample timestamps
- 产出 achieved measurement rate summary

禁止新增：

- 相机 ROI 数学换算细节
- preview 编码
- 浏览器 fps 统计展示逻辑

Lock:

- `src/workflow/live_run.py` 仍是唯一 coordinator
- 不拆出第二个 high-speed workflow service

### `src.storage` / `src.report`

新增职责：

- 在 `telemetry.csv` / `result.json` / summary 中落盘 achieved cadence
- 保留 measurement profile 和 bench-critical runtime facts

### `src.webapp`

新增职责：

- setup preview display path
- preview delivered-fps estimation
- run detail 中的 achieved-rate / capture-mode 对外映射

禁止新增：

- 通过 UI ROI 直接假装完成 camera-side ROI
- 在 route 层自己算 measurement cadence

## 3. State Flow Lock

### 3.1 Durable run status remains unchanged

`RunStatus` 不因为 temporal-sampling requirement 新增新的 durable enum。

继续使用：

```text
created
device_ready
preview_ready
definition_editing
run_ready
running
stopping
completed
failed
invalidated
aborted
```

### 3.2 Add explicit capture-mode semantics

新的状态表达通过 detail / telemetry 契约暴露，而不是污染 durable state：

```text
capture_mode:
  idle
  setup_preview
  measurement
  post_run_review
```

Lock:

- `setup_preview` 只用于操作者设置
- `measurement` 只在真正 run 执行时激活
- `post_run_review` 允许展示最后一帧、keyframe 或结果概览

### 3.3 Transition recommendation

```text
created
  -> device_ready
  -> preview_ready
  -> definition_editing
  -> run_ready
  -> running
  -> completed | failed | invalidated | aborted
```

Associated capture-mode transitions:

```text
idle
  -> setup_preview
  -> idle
  -> setup_preview
  -> measurement
  -> post_run_review
```

Lock:

- 进入 `running` 前，preview stream 必须停止或冻结并释放与 measurement path 冲突的资源
- `running` 阶段的优先级是 measurement cadence，不是 preview continuity
- run 结束后，页面优先进入 `post_run_review`，而不是自动回到 setup preview

## 4. API / Config Contract Lock

### 4.1 Config contract

Recommendation:

- 新增显式 profile split，而不是继续把所有相机参数塞在一个 live config 里。

Minimal locked shape:

```text
camera:
  setup_preview:
    target_preview_fps
    exposure_us
    gain_db
    display_max_width
    transport
  measurement:
    target_measurement_hz
    exposure_us
    gain_db
    acquisition_roi
    decimation
    binning
    artifact_capture_hz
```

Lock:

- `analysis_roi` / `metric_box` 继续属于 measurement definition
- `acquisition_roi` 归属于 camera measurement profile
- 二者不可混为一谈

### 4.2 API contract

`GET /api/runs/{run_id}` 必须成为 achieved-rate 和 capture-mode 的主读取入口。

新增或锁定的 detail 字段：

```text
capture_mode
rates:
  camera_resulting_fps
  preview_display_fps
  measurement_sample_hz
  artifact_capture_hz
  dropped_frame_count
measurement_profile:
  acquisition_roi
  decimation
  binning
  exposure_us
```

Recommendation:

- 不新增“切 mode”专用 API。
- 继续通过现有 preview / definition / start / stop 生命周期驱动 mode 切换。

### 4.3 Telemetry / artifact contract

Lock:

- `telemetry.csv` 必须可用于重建 sample cadence
- `result.json` 必须包含 achieved-rate summary
- 如可取得，记录：
  - camera resulting fps
  - effective measurement sample rate
  - dropped / skipped sample counters

### 4.4 Non-goals for API

当前不锁定：

- full-frame browser stream 的 50/100 fps API 承诺
- websocket-only telemetry channel
- 双路 preview + measurement 并发高频输出 API

## 6. Test Strategy Lock

### Layer 1: Contract / config tests

必须新增：

- setup preview profile 与 measurement profile 的 schema / typed-config 测试
- `acquisition_roi` 与 `analysis_roi` 不混用的 contract 测试
- achieved-rate response shape 测试

### Layer 2: Camera adapter tests

必须覆盖：

- measurement profile 参数映射
- camera-side ROI / decimation / binning capability fallback
- resulting-fps / payload reporting contract

### Layer 3: Workflow integration tests

必须覆盖：

- `run_ready -> running` 时 preview resource release / profile switch
- synchronized sample timestamp continuity
- achieved measurement cadence summary 计算
- measurement cadence 不达标时的显式 warning / failure semantics

### Layer 4: API tests

必须覆盖：

- `GET /api/runs/{run_id}` 返回 `capture_mode` 和 `rates`
- result / telemetry 中有 achieved-rate 信息
- run 中与 run 后 API 语义稳定

### Layer 5: Browser tests

必须覆盖：

- setup preview 仍满足 freeze / restart / overlay editing
- UI 能展示 achieved preview / measurement rate 或相应状态
- 运行时 UI 不把“监控帧率”误显示成“measurement sample rate”

### Layer 6: Bench validation

必须覆盖：

- 真机 `>= 50 Hz synchronized measurement` gate
- 同时记录：
  - measurement sample rate
  - camera resulting fps
  - acquisition ROI / exposure
  - 温度同步证据

Stretch-only:

- 真机 `>= 100 Hz synchronized measurement`

## 7. Phase Order Lock

### TS-1. Contract split and instrumentation skeleton

目标：

- 先把四类 rate concept 写进 core / web schema / config
- 补 `capture_mode` 与 achieved-rate contract skeleton

Done when:

- API / config / artifact 契约都能表达 setup vs measurement split

### TS-2. Camera measurement-profile plumbing

目标：

- 把 setup preview 和 measurement profile 真正连到 camera adapter
- 支持 measurement-side acquisition ROI / reduced readout wiring

Done when:

- workflow 可请求 measurement profile
- camera adapter 可返回实际 resulting facts

### TS-3. Workflow cadence accounting

目标：

- 在 live run coordinator 中落地 measurement timestamps、sample cadence summary、result reporting

Done when:

- `telemetry.csv` / `result.json` / API detail 可展示 achieved measurement cadence

### TS-4. Setup preview optimization

目标：

- 在不干扰 measurement plan 的前提下，提升 setup preview fluidity
- 评估更轻的 preview transport 和编码路径

Done when:

- setup preview 不再明显影响操作
- preview workstream 与 measurement workstream 在契约上保持分离

### TS-5. 50 Hz bench gate

目标：

- 在真实 bench 上证明 `>= 50 Hz synchronized measurement`

Done when:

- 真实 bench evidence 完整落盘
- achieved-rate、profile、温度同步证据可追溯

### TS-6. 100 Hz stretch review

前提：

- TS-5 已完成
- bench 显示仍有上探空间

目标：

- 决定是否进入 `100 Hz` stretch work

Lock:

- TS-6 不是当前实现承诺

---

## Final Recommendation

后续实现顺序应该严格按下面走：

1. 先做 TS-1 契约拆分
2. 再做 TS-2 camera measurement profile plumbing
3. 再做 TS-3 cadence accounting 和 achieved-rate reporting
4. 然后做 TS-4 setup preview 优化
5. 最后用 TS-5 bench gate 验证 `50 Hz`

这条顺序的核心原因是：

- 先把“什么叫完成”锁清楚
- 再去碰相机 profile 和高频链路
- 最后才拿 bench 证明，而不是反过来靠现场试错定义需求
