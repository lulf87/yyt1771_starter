# LU92XX Modbus RTU Requirement Update v1

Generated by `/office-hours` on 2026-03-21
Source protocol: `../../LU92XX温控表MODBUS-RTU通讯协议说明书(1).pdf`
Status: LOCKED_FOR_LU92XX_PHASE4

## 1. Why This Update Exists

The live-run plan originally treated the real temperature-control phase as blocked
on a missing serial protocol document.

That assumption is no longer true.

The LU92XX Modbus RTU PDF is now available in the workspace, so we can lock the
transport-layer and protocol-layer requirements for the real controller path.
At the same time, the supplied PDF pages only confirm the generic Modbus RTU
rules and examples. They do **not** yet provide an explicit LU92XX business
register map for:

- current temperature (`PV`)
- target temperature (`SV`)
- output enable / disable
- decimal scaling or signedness

This document exists to separate:

- what is now confirmed
- what we should build next
- what is still blocked on verified register mapping

## 2. Protocol Facts Confirmed By The PDF

The following items are directly supported by the protocol PDF.

- Transport is `RS485`, and the communication pattern is master/slave.
  The slave does not initiate communication. Unknown commands are ignored.
  Source: pp. 3-4.
- Frame format is `START + ADD + CS + DATA + CRC + END`.
  Source: p. 4.
- Device address is one byte and ranges from `1` to `255`.
  Source: p. 4.
- Function code is one byte. The document lists supported codes:
  `01H`, `02H`, `03H`, `05H`, `06H`, `0FH`, `10H`.
  Source: pp. 4-5.
- `03H` reads one or more consecutive 16-bit registers.
  One register is 2 bytes, high byte first, and one request may read up to
  125 registers.
  Source: pp. 5-6.
- `06H` writes one 16-bit register.
  Source: pp. 5-7 and p. 11 example.
- `10H` writes multiple consecutive 16-bit registers.
  Source: pp. 5-7 and p. 12 example.
- CRC uses `CRC-16`.
  The CRC value is transmitted as low byte first, high byte second.
  Source: pp. 7-8.
- Serial data frame uses 8 data bits.
  With parity, the frame uses 1 stop bit.
  Without parity, the frame uses 2 stop bits.
  Source: p. 3.
- Exception responses set the high bit of the function code.
  The document explicitly lists:
  `01` illegal function,
  `02` illegal data address,
  `03` illegal data value.
  Source: pp. 12-13.

## 3. Office-Hours Decision

### 3.1 Status quo

The repo already has:

- `TempReader`
- `TempControllerPort`
- a mock temp controller
- a live-run workflow that expects:
  - `set_target_temperature()`
  - `start_output()`
  - `stop_output()`
  - `read()`

The missing piece is no longer "some serial driver".
The missing piece is a **LU92XX-specific control path** that can satisfy the
existing workflow contract without leaking Modbus details into `workflow` or
`webapp`.

### 3.2 Narrowest useful wedge

The first real-hardware wedge is:

1. open the configured RS485 serial port
2. read the current temperature from the LU92XX
3. write the target temperature to the LU92XX
4. enable controller output
5. disable controller output
6. turn timeouts, exception codes, and bad replies into clear adapter errors

### 3.3 Product decision

Do **not** build a generic "serial scripting engine" or "multi-device protocol
framework" in this phase.

Do build one adapter locked to:

- LU92XX
- RS485
- Modbus RTU
- the existing `TempReader` + `TempControllerPort` boundary

Future device diversity should be handled by adding another adapter later, not by
over-generalizing the first real device path.

## 4. Locked Requirement Changes

### 4.1 Adapter ownership

The real hardware adapter for this phase should be:

- `src/temp/lu92xx_modbus_rtu_controller.py`

Suggested class name:

- `LU92XXModbusRtuController`

It should implement both:

- `TempReader`
- `TempControllerPort`

### 4.2 Boundary lock

The following rules are now locked:

- `workflow` must continue to call only:
  - `set_target_temperature(celsius)`
  - `start_output()`
  - `stop_output()`
  - `read()`
- `webapp` must not construct Modbus frames.
- `workflow` must not contain device register addresses or CRC logic.
- all LU92XX protocol packing/parsing belongs inside `src/temp/*`.

### 4.3 Command strategy lock

The protocol document confirms the transport-level command families, but the
business register map is still pending.

Therefore the adapter must support this design:

- temperature read path uses configured `03H`
- target write path uses configured `06H` or `10H`
- output enable / disable uses configured `05H`, `06H`, or `10H`

The code must not hard-code which write command is used for "set target" or
"start output" until the actual LU92XX register map is verified.

### 4.4 Config contract lock

The live profile should move from a generic temp backend name to a device-bound
backend name.

Recommended config shape:

```yaml
temp:
  backend: lu92xx_modbus_rtu
  protocol: modbus_rtu
  slave_address: 1
  serial:
    port: COM5
    baudrate: 9600
    bytesize: 8
    parity: N
    stopbits: 1
    timeout_ms: 500
  register_map:
    process_value:
      function_code: 3
      start_address: TBD
      register_count: TBD
      scale: TBD
      offset: 0.0
    target_value:
      function_code: TBD
      start_address: TBD
      register_count: TBD
      scale: TBD
      offset: 0.0
    output_enable:
      function_code: TBD
      start_address: TBD
      register_count: 1
      on_value: TBD
      off_value: TBD
```

`TBD` above is intentional.
These values must not be invented from generic Modbus examples.
They need a verified LU92XX register table or a successful device-side read/write
validation record.

### 4.5 Error handling lock

The adapter must distinguish at least these failure classes:

- serial port open failure
- timeout / no response
- CRC or malformed frame
- exception response `01`
- exception response `02`
- exception response `03`
- empty or short register payload
- configured register map missing required fields

These errors must fail clearly and must not be silently converted into a fake
temperature or a fake "output started" state.

### 4.6 Operator serial-port selection lock

For the Web workstation, the LU92XX serial port must be selectable from the UI.
The operator should not have to edit a backend YAML file during normal setup.

Locked behavior:

- Web exposes a serial-port discovery endpoint backed by the local Python
  runtime's visible serial ports.
- The temperature setup panel exposes:
  - refresh available serial ports
  - choose one visible port
  - apply the port and immediately read current temperature
- Applying a port updates only the current service process:
  `runtime_config.live.temp.serial.port`.
- Applying a port must not write tracked or local YAML files.
- The shared temperature controller must be reset after a port change.
- The new port is accepted only if a temperature read succeeds.
- If the read fails, the service rolls back to the previous port and surfaces a
  clear error to the UI.
- This feature is active only for the `lu92xx_modbus_rtu` backend. Mock and
  offline profiles must not pretend that a hardware serial port was selected.

## 5. Test Contract

The real-device phase should add at least:

- `tests/temp/test_lu92xx_modbus_rtu_controller.py`
- `tests/webapp/test_profile_api.py` coverage for serial-port listing,
  process-local selection, rollback on failed read, and unknown-port rejection
- `tests/webapp/test_ui_shell.py` coverage for the Web serial-port controls

Minimum coverage:

- open/connect failure
- `03H` readback parsing
- `06H` single-register write formatting
- `10H` multi-register write formatting
- exception response mapping
- timeout / no response mapping
- profile-driven register map validation
- `close()` can be called repeatedly

## 6. Remaining Unknowns

The following items are still unresolved and remain blockers for claiming the
real LU92XX path is complete:

- actual register address for current temperature
- actual register address for target temperature
- whether target temperature is one register or multiple registers
- actual output enable / disable address and command family
- decimal scaling rule, offset rule, and signedness rule
- deployed device serial settings:
  - baudrate
  - parity
  - stopbits
  - slave address
- whether successful write must be followed by readback confirmation

Until those values are verified, we can lock code structure and config structure,
but we cannot claim the LU92XX device integration is finished.

## 7. Done Criteria For The Hardware Phase

Phase 4 should be considered complete only when all of the following are true:

- the adapter can open the configured LU92XX serial port
- `read()` returns a real `TempReading` from the configured `03H` mapping
- `set_target_temperature()` writes via the configured LU92XX mapping
- `start_output()` and `stop_output()` work via the configured LU92XX mapping
- protocol exceptions and transport failures surface as clear errors
- `workflow` and `webapp` do not need any LU92XX-specific branching
- the verified register map is recorded in config or in a dedicated mapping file
